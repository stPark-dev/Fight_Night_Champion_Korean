# 시합 중 멈춤 조사 (2026-10-22 ~ 23)

## 메모리 설정 분석 (2026-10-23) — 원인 미확정

EBOOT 안에 텍스트로 들어 있는 EA MemoryFramework 설정(`finalmemoryconfig.h`, ELF 0x12a6d72~, 사본 `work/memory_config_embedded.txt`)의 관련 부분:

```
AddAllocator  FONT_GEN      PPMallocMutex [ size=1M ... ]     ← 폰트 엔진 전용 풀
AddAllocator  OVERFLOW_GEN  PPMallocMutex [ size=10M ... ]    ← 공용 넘침 풀
AddAllocator.ps3  FRONTEND_GEN  HighLow256K [ size=24M ... ]
AddCategoryAllocator  Render::Font     FONT_GEN → OVERFLOW_GEN
AddCategoryAllocator  Sys::FileSystem  REPLAY_GEN → GLOBAL_GEN → FRONTEND_GEN  [ allowfail=1 ]
```

- 정지 지점의 호출 경로: 파일 입출력 작업 스레드(`/dev_hdd0`)가 끝난 작업의 콜백(`0x4a5010`)을 부르고, 콜백이 작업 객체+0x18의 버퍼에 쓴다. 이 버퍼가 NULL이었다. 파일 시스템 할당은 실패가 허용되므로(allowfail=1), 버퍼 할당 실패로 보인다.
- **가설 1 (기각)**: 폰트가 FONT_GEN(1MB)을 넘쳐 OVERFLOW_GEN을 잠식한다.
  - `FONT_GEN size=1M → 6M` 패치를 적용하고, 부팅 로그에서 0x600000 할당을 확인했다.
  - 그래도 시험 1회차 9분 35초에 같은 지점에서 정지했다(5회 중 1회, `work/runlogs/fix/`). 기각하고 패치를 뺐다.
- 스트레스 관찰:
  - 한글 11,172자(폰트 +35MB): 부팅 17~20초에 정지
  - 4,700자(+15MB): 28초에 정지
  - 2,350자(+7MB): 3분 시합에서 정지 없음(2회)
- **가설 2 (지지됨)**: 폰트 파일 자체가 FRONTEND_GEN(24MB)에 올라가, 파일 시스템의 마지막 대체 풀을 줄인다.
  - +15MB 폰트 변형으로 부팅해 3분 시합을 2회씩 돌렸다(`work/runlogs/quick2/`).

    | 설정 | 결과 |
    |---|---|
    | 원본 | 2/2 정지 (약 27초) |
    | FONT_GEN 6M | 2/2 정지 |
    | GLOBAL_GEN 20M | 2/2 정지 |
    | **FRONTEND_GEN 32M** | **0/2 정지** |

- **FRONTEND_GEN 24M → 28M 적용 결과 (기각)**: 부팅 로그에서 0x1c00000 할당을 확인했다. 그런데도 4회 중 2회(17분 40초, 9분 47초) 같은 지점에서 정지했다(`work/runlogs/fix2/`). 패치를 뺐다.
  - 결론: 큰 폰트(+15MB)의 부팅 직후 정지는 FRONTEND_GEN 부족 때문이 맞다. 그러나 실제 한글판(+2.6MB)의 시합 중 정지는 그것과 다른 현상이다.
- 리플레이 메타데이터(`dev_hdd1/.../replay_metadata/1.md`)에는 영문 선수 이름만 있다. 한글 문자열은 들어가지 않는다.

## 정지 직전 동작 (2026-10-23)

- 세 번의 정지 모두 같은 흐름이었다. 정지 스레드가 약 24초마다 리플레이 썸네일(`/dev_hdd1/replay/<n>/1/<k>.jpg`)을 쓰고, 그 직후 5~24초 안에 정지했다.
- **JPEG 버퍼 넘침 가설 (기각)**: 썸네일 크기를 비교했다.

  | 빌드 | 최대 크기 |
  |---|---|
  | 원본 | 0x2fc39 |
  | 한글판 | 0x2f926 |
  | fe 원본 변형 | 0x31820 (그래도 정상) |

  원본이 오히려 크거나 비슷하므로 기각한다.
- 콜백 `0x4a5010`은 OPD `0x16c8d60`로만 참조된다. 등록하는 곳은 `0x4a5b20`·`0x4a625c` 함수의 비동기 쓰기 호출(`bl 0x7b9830`, 콜백 r8, 사용자 데이터 r9)이다.
  - 이 쓰기 객체는 버퍼 2개를 번갈아 쓴다(+0xaec[i], 바쁨 플래그 +0xaf8[i], 인덱스 +0xaf4). 사용자 데이터는 "끝나면 지울 바쁨 플래그 주소"다.
  - 콜백은 `*(job+0x18)`(= 플래그 주소)에 0을 쓰는데, 정지 시 job은 살아 있고 +0x18만 0이었다.
  - 따라서 할당 실패보다는, **진행 중 작업 구조체가 재사용·덮어써지는 경쟁 상태**일 가능성이 크다.
  - EAIO 스트림 쓰기(리플레이 캐시 `/dev_hdd1`)이고 번역 데이터는 직접 거치지 않는다. 한글판에서 프레임 타이밍이나 메모리 배치가 달라져 경쟁 창이 넓어졌을 가능성이 있다.

## 오류 지점 분석

```
004a5010: lwz r3, 0x18(r3)   ; 객체+0x18 의 버퍼 포인터
004a5014: li  r4, 0
004a5018: stb r4, 0(r3)      ; 버퍼 첫 바이트 = 0  ← 포인터가 NULL 이라 0x0 에 쓰기
004a501c: blr
```

- 문자열이나 버퍼를 비우는 작은 함수다. 버퍼가 할당되지 않은 객체(포인터 NULL)에 대해 불렸다.
- **할당 실패를 확인하지 않는 코드**로 보인다.
  - 메모리가 빠듯할 때만 드물게 터진다는 설명과 맞는다.
  - 원본에서는 재현되지 않았다.
- 한글화로 늘어난 상주 데이터는 다음과 같다.
  - UI 폰트 8종: 628,560 B → 3,252,708 B (**+2.6 MB**). 한글 1,031자 병합 때문이다.
  - 번역 DB: 602,572 B → 678,380 B (+76 KB)
- 폰트를 원본으로 되돌린 `nofe`는 3회 모두 정상이었다. 다만 표본이 적어 결론을 낼 수는 없다. 멈춤 빈도는 대략 6~8회에 1회다.

## 임시책: 콜백 NULL 확인 (2026-10-24)

- 패치(`tools/fnc/eboot.py` `NULLCHECK_PATCHES`):
  - `0x4a5010`: `lwz r3,0x18(r3) / cmpwi r3,0 / beqlr / b 0x16a2cf0`
  - 동굴 `0x16a2cf0`: `li r4,0 / stb r4,0(r3) / blr`
